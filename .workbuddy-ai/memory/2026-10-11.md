## 对话 3 — 工程规范、架构补齐、性能方案

5. **特效与性能的矛盾** —— 明知特效多会卡顿，但**依然要用**。理由：「互联网上肯定有解决这些问题的办法」，要求找到方案
6. **项目定位升级** —— 不是普通宣发，是「**大厂软件宣发 + 美术级炫酷特效**的结合」。大厂宣发该有的（信息架构、CTA、功能介绍）要有，美术宣发的视觉冲击也要有；技术选型「一定是要用最成熟的、最好的」
7. **文件夹要整洁** —— 「让别人一眼看清这到底是干嘛的」

### 我做了什么

1. **建目录骨架**（`mkdir -p`）：

2. **写 `docs/CODE_STYLE.md`（项目法律）**，7 条红线：

3. **写 `docs/ARCHITECTURE.md`**：
   - 完整技术选型表（Next.js 15 / TS strict / Tailwind 3.4 / Framer Motion / GSAP / Three.js + R3F / postprocessing）

   - **回答「要不要后端」→ 结论：不写传统后端**（详见下）

4. **写 `docs/PERFORMANCE.md`**（回应用户「特效和卡顿能否兼得」）：

   - 性能预算表（首屏 JS ≤170KB、LCP <2.5s、CLS <0.1、mid 档 ≥50fps）
   - 特效注册表机制（一键开关、防膨胀）
   - **「内容层 SSR 直出 + 表现层懒加载特效」双层结构**（大厂宣发 + 美术特效共存的答案）

## 对话 4 — 用户纠正：代码行数上限定得太死

### 用户说了什么

- 吐槽我把上限定得太苛刻：「300 / 150 / 60 行，你是不是有点苛刻了呀？」
- 理由：**「有些 TSX 文件确实要 400-500 行，得根据具体情况具体实现，不能硬指标一直砍」**
- 明确要求：不能说超过 300 行就全咔掉，这种不行

### 我做了什么（采纳并修正）

1. **`docs/CODE_STYLE.md` R1 重写** —— 从「硬上限」改为「软提醒 + 真红线 + 豁免」三段式：

   | 类型 | 提醒线（不阻断） | 真红线（必须处理） |
   |---|---|---|
   | `.ts/.tsx` 文件 | 300 行 | **600 行** |
   | 单个 React 组件 | 200 行 | **400 行** |
   | 单个函数 / Hook | 80 行 | **150 行** |
   | CSS 文件 | 400 行 | **800 行** |

2. **加了豁免机制**：文件顶部写注释说明理由 → 登记进 `CODE_STYLE.md` 豁免表 → 加进 `eslint.config.mjs` 的 `LARGE_FILE_ALLOWLIST`
3. **`eslint.config.mjs` 修正**：`max-lines: 600`（error）、`max-lines-per-function: 150`（error）、`complexity` 12→15、`max-params` 4→5；新增 `LARGE_FILE_ALLOWLIST` 数组与对应 override 块
4. 更新提交前自检清单与「自动化保障」说明
5. 同步更新 `MEMORY.md` 第 4.5 节

### 达成的共识（重要，后续必须遵守）

> **行数不是目的，可维护性才是。**
> 一个 450 行但职责单一、分区清晰的文件，远好过硬拆成 5 个碎片。
> 真正防屎山靠：单一职责、圈复杂度、嵌套深度、分层 —— 行数只是辅助信号。

**唯一绝对不允许：几千行的文件**（不是"有理由的长"，是设计失控）。

ESLint 只卡真红线，提醒线交给 review 讨论，不阻断开发。

## 对话 5 — 用户澄清：真正的红线是「职责混杂」，不是行数

### 用户说了什么（这是本项目最重要的一次澄清）

用户进一步澄清了对话 4 的真实意图：

- **真正在意的不是行数，是职责混杂**：「一个文件里本可以再建文件夹/文件分开写，却没建，而是硬生生把两个、三个东西堆积在一个文件里，那确实不行」
- **核心原则**：「能分开写一个效果、一个功能的话，你肯定要分开写」
- **目的**：方便后续维护，自己一眼看懂，**也让 Agent 读取时非常快、一看就知道是什么情况**
- 强调：整个项目里「哪个东西是干嘛，哪个东西是干嘛，都非常清楚」

### 我做了什么

1. **`docs/CODE_STYLE.md` R2 大幅扩写为「职责分离」，标为本项目最重要的一条**：
   - 核心原则：一个概念 = 一个文件（组件/特效/Hook/领域工具/section 各有归属）
   - **5 条「必须拆」的判据**：
     1. 一个文件 ≥2 个 React 组件
     2. 混了不同层职责（数据获取+渲染+动画）
     3. 混了不同领域逻辑（粒子+滚动）
     4. **出现分区注释**（`// ===== 下面是 XX 部分 =====`）← 最明显信号
     5. 有能独立命名的概念
   - 加了正/反面代码示例（反面：HeroSection.tsx 里塞组件+Hook+配置+粒子逻辑；正面：Hero/ 目录拆分）
   - 新增「**Agent 友好**」小节（见下方共识）
   - 新增「命名自解释」正反对照表
2. **装上机器检测**：`eslint-plugin-react` 的 `react/no-multi-comp`（warn 级）—— 一个文件多组件即报警
   - `package.json` 加 `eslint-plugin-react: ^7.37.0`
   - `eslint.config.mjs` 加 `import react`、`plugins: { react }`、`settings.react.version: '19.0'`
   - 用 `warn` 不用 `error`：合法的私有小组件交给 review 判断，与上一条「不硬卡」的精神一致
3. 更新提交前自检清单：把「职责分离」和「文件名自解释」提到最前面（⭐ 标记）
