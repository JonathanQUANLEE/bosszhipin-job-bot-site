# 性能策略：特效拉满，但不卡

> **核心结论：能兼得。**
> 卡顿不是"特效多"导致的，是"特效在错误的时间、以错误的强度、跑在错误的设备上"导致的。
> 下面这套方案是行业内做重特效落地页的标准做法（Linear / Vercel / Awwwards 级别站点都在用）。

---

## 一、总体策略：三条铁律

### 铁律 1：首屏"轻"，重特效"晚"

访客对**首屏速度**的感知最敏感。所以：

| 阶段 | 加载什么 | 手段 |
|---|---|---|
| 首屏（0-1s） | 文案、按钮、骨架屏、**纯 CSS 动画** | 同步加载，体积极小 |
| 首屏可见后 | Three.js / GSAP / 粒子 / 后处理 | `dynamic(..., { ssr: false })` 异步 chunk |
| 滚动进入视口 | 各 section 的重特效 | `IntersectionObserver` 触发 |

> 用户看到炫酷特效时，页面**早就加载完了**。
> 他感知到的是"这站好快，而且好炫"，不是"卡"。

### 铁律 2：特效强度跟着设备走

**不做一刀切。** 检测设备性能分成 4 档，每档一套参数：

| 档位 | 判定依据 | 粒子数 | DPR 上限 | 后处理 | 目标帧率 |
|---|---|---|---|---|---|
| `high` | 独立显卡 / 高核心数 / 桌面端 | 8000 | 2.0 | 全开 | 60fps |
| `mid` | 主流笔记本 / 中端手机 | 3000 | 1.5 | 仅 Bloom | 60fps |
| `low` | 低端设备 / 内存 < 4GB | 800 | 1.0 | 关闭 | 30fps |
| `off` | `prefers-reduced-motion` / 省电模式 | 0 | — | 关闭 | 静态降级 |

实现位置：`src/lib/performance/` + `src/hooks/use-performance-tier.ts`

### 铁律 3：看不见就别算

页面切到后台、section 滚出视口、**任何**看不见的情况，立即停掉渲染循环。

## 二、具体技术手段（12 条）

| # | 手段 | 解决什么问题 |
|---|---|---|
| 1 | **代码分割**：three.js 单独 chunk，懒加载 | 首屏体积不被 3D 引擎拖垮 |
| 2 | **IntersectionObserver 门控**：进入视口才初始化 WebGL 上下文 | 避免一进页面就开 5 个 canvas |
| 3 | **DPR 钳制**：`Math.min(devicePixelRatio, 2)`，低端降到 1 | 4K 屏上渲染像素数直接砍 75% |
| 4 | **单一 rAF 调度器**：全站共用一个 requestAnimationFrame 循环 | 避免 10 个特效各起一个循环互相抢帧 |
| 5 | **visibilitychange 暂停**：切后台立即停 | 省电，回来不卡 |
| 6 | **只动 transform / opacity** | 走 GPU 合成层，不触发 layout / paint |
| 7 | **后处理降分辨率**：Bloom 等在 1/2 或 1/4 buffer 上算 | 后处理是最贵的一环 |
| 8 | **`prefers-reduced-motion` 尊重** | 无障碍 + 晕动症用户，也是合规要求 |
| 9 | **纹理 / 几何体复用**：不重复创建，走对象池 | 避免 GC 抖动导致的间歇性卡顿 |
| 10 | **`will-change` 克制使用**：只在动画期间加 | 滥用会导致显存爆炸 |
| 11 | **字体自托管**：`next/font` + `font-display: swap` | 消除 FOUT/FOIT 抖动 |
| 12 | **图片 WebP/AVIF + 响应式尺寸** | 截图素材不做优化会吃掉一半加载时间 |

## 三、性能预算（写死，超了就打回）

| 指标 | 预算 | 检测方式 |
|---|---|---|
| 首屏 JS（gzip） | **≤ 170 KB** | `next build` 输出 |
| 首屏 CSS（gzip） | **≤ 30 KB** | `next build` 输出 |
| 单个懒加载特效 chunk | **≤ 150 KB** | Bundle Analyzer |
| LCP | **< 2.5 s** | Lighthouse |
| CLS | **< 0.1** | Lighthouse |
| INP | **< 200 ms** | Lighthouse |
| 运行时帧率（mid 档） | **≥ 50 fps** | DevTools Performance |
| 主线程长任务 | **0 个 > 200ms** | DevTools |

> 每引入一个新特效，先问：**它占多少预算？**
> 预算超了就砍特效，不砍体验。

## 四、特效治理：注册表机制

**不允许**特效散落在各处各自初始化。必须注册到统一注册表：

```ts
// src/config/effects.ts
export const EFFECT_REGISTRY = {
  heroParticleField: {
    enabled: true,
    tier: { high: {...}, mid: {...}, low: {...}, off: 'disabled' },
    chunk: () => import('@/components/effects/ParticleField'),
  },
  // ...
} as const;
```

好处：
- **一键开关**任何特效（线上出问题可以立刻降级）
- **一眼看清**全站有哪些特效、各占多少
- 新增特效必须登记，防止偷偷膨胀

## 五、"大厂宣发 + 美术级特效"如何共存

你提到想结合两者——这正好对应**双层结构**：

```
┌─────────────────────────────────────┐
│  内容层（大厂宣发该有的）              │
│  · 清晰的信息架构                     │
│  · 一句话价值主张                     │
│  · 功能列表 / 截图 / 快速开始          │
│  · GitHub + 下载 CTA                 │
│  · 免责声明、许可证                    │
│  → 必须无 JS 也能读懂（SSR 输出）      │
├─────────────────────────────────────┤
│  表现层（美术级特效）                  │
│  · 粒子 / 3D / 滚动叙事 / 后处理       │
│  · 全部懒加载、可降级、可关闭          │
│  → 锦上添花，不阻断信息获取            │
└─────────────────────────────────────┘
```

**关键**：内容层是 SSR 直出的，就算特效全部加载失败，
页面依然是一个完整、可读、专业的产品页——这就是大厂宣发的底子。
特效是在这个底子上叠加的美术层。

> 这样即使访客设备很烂、网络很差，他拿到的仍是一个**及格的产品页**；
> 设备好的访客拿到的则是**惊艳的作品**。
> 两边都不损失。

## 六、每次加特效前的自检

- [ ] 它懒加载了吗？
- [ ] 它进视口才初始化吗？
- [ ] 它有 4 档降级参数吗？
- [ ] 它尊重 `prefers-reduced-motion` 吗？
- [ ] 它登记到 `EFFECT_REGISTRY` 了吗？
- [ ] 它跑在统一 rAF 调度器上吗？
- [ ] 它的 chunk 体积在预算内吗？
- [ ] 关掉它，页面还是完整可读的吗？
